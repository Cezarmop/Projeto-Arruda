Setor de Compras

Contratos de integração

As mensagens que o Compras troca com os outros setores, no mesmo modelo dos contratos do Financeiro. Cada mensagem tem um schema (XSD) e um exemplo, e pode ir pela API REST (padrão) ou pelo socket da turma, com o mesmo XML e as mesmas regras. Os endpoints de cada serviço estão no Registry do Compras. Não precisa de login para consultar. Abrir o Controle de Compras.

Estoque

Compras → Estoque · envio (o Estoque busca)

Recebimento

Cada baixa feita no Compras: o que chegou, de qual pedido e fornecedor, com status TOTAL ou PARCIAL. Leva também nota fiscal, quantidade pedida, custo, avaria e lote, quando houver. O Estoque dá entrada no saldo.

REST GET /v1/recebimentos?desde=<seq> · um XML: GET /v1/recebimentos/{seq} · Socket: arquivo para o ID do Estoque

Estoque → Compras · resposta

Confirmação de recebimento

A resposta ao Recebimento, recebimento por recebimento, pela mesma referencia: ACEITO, DIVERGENTE (com a quantidade contada), REJEITADO ou DUPLICADO. Se o arquivo inteiro não puder ser processado, vem <erro> no lugar do resultado.

REST POST /v1/confirmacoes-recebimento (ou /v1/mensagens) · Socket: arquivo .xml para #compras

Previsão de entrega

Pedidos ainda não recebidos, com a data prevista e os itens que faltam chegar, para o Estoque reservar espaço e conferente. Status AGUARDANDO, EM_TRANSITO, ATRASADA ou CANCELADA. Uma publicação nova do mesmo pedido atualiza a previsão.

Compras → Estoque · consulta

Disponibilidade de produto

Antes de comprar, o Compras pergunta ao Estoque quantas unidades de um produto estão disponíveis. A consulta não reserva nem movimenta o saldo. É o mesmo formato que o Estoque já responde ao Patrimônio, sem namespace.

<consultaDisponibilidade>
  <idConsulta>CONS-COMPRAS-000001</idConsulta>
  <produtoCodigo>MONITOR-001</produtoCodigo>
</consultaDisponibilidade>

O Estoque copia idConsulta e produtoCodigo e devolve <produto> (nome e quantidadeDisponivel) ou <erro>, nunca os dois. Resposta idêntica reenviada não muda nada; resposta diferente para a mesma consulta é recusada, e o Compras gera outra consulta.

REST: consulta em GET /v1/consultas-disponibilidade?desde=<seq>; resposta em POST /v1/respostas-disponibilidade (ou /v1/mensagens) · Socket: arquivos nos dois sentidos

Saldo de produtos

O saldo no formato do próprio Estoque (<estoque versao="2">). O Compras também busca o saldo sozinho em GET /api/xml do Estoque, então o envio é opcional.

REST POST /v1/saldos-estoque (ou /v1/mensagens)

Financeiro

Com o Financeiro, quem define os formatos é o Finanweb: o Compras chama a API dele com a chave do setor compras. Veja os contratos do Financeiro.

Compras → Financeiro · envio, consulta e aviso

Compra, pendências com fornecedor e aviso de pagamento

Cada pedido vira uma conta a pagar (POST /api/v1/compras, saida-v2 em JSON). As pendências de um fornecedor são consultadas em GET /api/v1/pendencias?origem=compras, com resposta na hora. Os avisos de pagamento são buscados pelo servidor do Compras em GET /api/v1/avisos-pagamento?origem=compras&desde=..., no máximo uma vez por minuto, e marcam a compra como paga.

Opcional: se o Financeiro preferir empurrar, o Compras aceita POST /v1/avisos-pagamento (XML urn:finanweb:aviso-pagamento:1.0 ou o mesmo JSON do Finanweb) e POST /v1/respostas-pendencias.

Como integrar

Os envios de outros setores entram na caixa de entrada do Compras e são aplicados quando a tela do Compras lê a caixa (a cada 20 segundos). As publicações do Compras ficam disponíveis até o setor buscar.

REST (padrão)

  • Base: /compras/api. Um GET /v1 lista as rotas e GET /v1/saude mostra o estado. Contrato completo em OpenAPI 3: openapi.json. CORS liberado para chamadas do navegador.
  • Autenticação: cabeçalho Authorization: Bearer <chave>. A chave é pedida ao Compras por mensagem privada para #compras e identifica o setor. Sem chave ou chave errada: 401. Rota de outro setor: 403.
  • Envios (POST, Content-Type: application/xml): o XML do contrato no corpo, até 1 MB. O tipo é descoberto pela raiz e pelo namespace, e os contratos com XSD são validados no servidor. Respostas: 202 { "ok": true, "seq": 12, "duplicada": false }; o mesmo XML de novo, 200 com "duplicada": true; fora do contrato, 422 com { "ok": false, "erro": "...", "detalhes": [...] }. Corpo grande demais: 413; tipo errado: 415.
  • Buscas (GET): paginação por cursor. Mande ?desde= com o último seq lido (0 na primeira vez) e guarde o ultimo da resposta. limite vai de 1 a 200 (padrão 50). Cada item traz seq, referencia, publicadoEm e o xml.
  • Frequência: buscar a cada 20 a 60 segundos é suficiente.
# Estoque: buscar recebimentos novos
curl -H "Authorization: Bearer CHAVE_DO_ESTOQUE" "/compras/api/v1/recebimentos?desde=0"

# Estoque: devolver a confirmação
curl -X POST -H "Authorization: Bearer CHAVE_DO_ESTOQUE" -H "Content-Type: application/xml" \
     --data-binary @confirmacao-recebimento-v1.xml "/compras/api/v1/mensagens"

Socket (alternativa)

  1. Gere o XML seguindo o exemplo da mensagem e valide contra o XSD, por exemplo: 
    xmllint --noout --schema confirmacao-recebimento-v1.xsd confirmacao.xml
  2. Envie como arquivo .xml para #compras no servidor da turma. O XML vai em uma linha só, sem quebras entre as tags.
  3. O Compras só recebe pelo socket enquanto a tela dele estiver aberta e conectada. Pela API, a mensagem fica guardada na caixa de entrada.

Roteiro de teste

  1. Peça a chave e confira com GET /v1/recebimentos?desde=0 (deve voltar 200).
  2. Escolha um produto que exista no Estoque e combine o código com o Compras.
  3. Responda a consulta de disponibilidade com o mesmo idConsulta.
  4. Busque o recebimento-v1 depois da baixa e devolva a confirmação.
  5. Confira no Compras que a entrada ficou aceita, divergente ou rejeitada.

O 202 confirma só a transmissão. A integração está confirmada quando o resultado aparece no sistema do outro setor.

Regras comuns

  • Cabeçalho: igual ao do Financeiro, com empresa, cnpj, origem, dataArquivo e usuario.
  • Identificação: fornecedor por CPF ou CNPJ, só dígitos (11222333000181). Nos contratos com o Estoque, o documento é opcional.
  • Produto: SKU em maiúsculas, dígitos e hífen, até 40 caracteres (NOTEBOOK-001), a mesma regra do Estoque.
  • Quantidades, valores e datas: quantidades inteiras e positivas; valores com ponto e duas casas (3499.90); datas no formato AAAA-MM-DD.
  • Origem: o nome do setor, em minúsculas (compras, estoque, financeiro), igual na API e no socket.
  • Referência: o identificador do registro no Compras (REC-1001-7 no recebimento, PC-1001 na previsão). O par origem + referência identifica o registro, então reenviar não duplica nada.
  • Totalizador: qtdRegistros e quantidadeTotal (soma das quantidades) fecham cada envio.

Mudanças e dúvidas

  • O Compras define os formatos das mensagens com o Estoque; os do Financeiro são definidos pelo Finanweb.
  • Depois de combinado, um formato só muda com versão nova (outro número no namespace ou /v2), e a versão anterior continua aceita.
  • Dúvidas, sugestões e pedidos de chave: mensagem privada para #compras no servidor da turma.
